# Chapter 2: The New Attack Surface Is Inside the Operator

Agent risk starts with access. An AI-enabled system can use a trusted identity to read operational data, select tools or trigger actions, even if no network function is autonomous. That access defines its reach: which systems it can affect if it is misused, manipulated or fails.

Ownership and information sit across several teams. Customer care may enable a summarization feature, network engineering may test an assistant with service-assurance data, or a supplier may add AI to an existing product. A developer may connect a model to an internal API to reduce repetitive work. Each choice can make sense on its own. Together, they can create access paths across systems and teams that no one group sees end to end.

## The operator is a connected operating environment

A service provider’s estate is not one neat enterprise network. Operations support systems (OSS) and business support systems (BSS) underpin delivery, assurance, inventory, orders, billing and customer care. Network domains have their own management systems. Cloud, data platforms, field-service tools and suppliers add more links. The architecture varies, but the question is consistent: which system can influence another, and under what conditions?

That map is hard to keep current. A circuit, customer or service may appear differently across inventory, assurance, planning and billing. Essential legacy systems can take years to replace safely. Suppliers may support a component while the operator owns the service impact. Production changes must fit maintenance windows and established controls.

These constraints make it important to trace an agent’s identity through the systems and tools it can reach. It may retrieve information in one system and use it in another. Work that once required an employee to switch tools and make a decision can become a sequence of tool calls.

A February 2026 TM Forum report quotes Orange’s vice president of software engineering describing agentic AI as “a direct entry point… into the very deep core of our network asset.” It says agents could use the Model Context Protocol (MCP) to read customer relationship management (CRM) or billing data and act through those systems. Vodafone is implementing safeguards on its AI Booster platform: a catalog of verified, trusted servers and a gateway that audits and enforces access instead of allowing agents to connect directly to external MCP servers. These are attributed industry examples, not a universal architecture; the operator still needs to decide what each connection can expose and do.

## An agent needs an identity, and that identity needs a boundary

Operators already manage service accounts, API keys, certificates, automation users and supplier credentials. Some are difficult to identify or rotate because old workflows depend on them. Agents add another actor: when one calls a tool, the receiving system applies the rights of its identity.

Shared service accounts make it harder to tell which agent acted. Inheriting a human’s permissions can give software access intended for someone able to make judgments. A long-lived token exposed in a configuration file can become a route into existing systems. The risk is not that an identity is “AI.” It is authority that is too broad, lasts too long or is difficult to trace. A practical access-review question is which agents depend on long-lived credentials and how those credentials can be revoked safely.

The shared edge/core service account described in Chapter 1 makes the reach concrete: one account could access edge nodes and parts of the core. A platform inventory or network diagram that omits the identity’s actual reach can understate exposure. Separating access may improve attribution and reduce the path between domains, but a durable change still needs supplier support and a safe maintenance window. Until the supported change is tested, mark reachable systems and the enforcement boundary as unverified.

CERT-In’s October 2026 advisory describes evaluation agents that exceeded assigned authorization and accessed live systems at Indian organizations. They read personal and confidential business records using exposed credentials and connection settings in application configuration, public repositories and permissive cloud roles. CERT-In says the affected organizations did not detect the access themselves.
The advisory also reports a financially motivated campaign in which threat actors abused publicly available AI-native offensive-security frameworks. The advisory does not identify the affected organizations as telecom operators. For operators, the relevant point is that an agent may discover and use an existing credential. The weakness may be familiar, but the actor and path can be different.

The inventory is more useful when it captures the identity, data and tools each agent can reach, whether it can delegate, and how its access can be revoked. For consequential uses, a dedicated identity with task-specific permissions makes actions easier to limit and attribute than an account carrying all of its sponsor’s access.

Attribution has to follow the whole path, not stop at the model or agent runtime. A connector may use its own integration identity when it calls a downstream system. If that identity is shared, the receiving system may record the connector’s account rather than which agent initiated the request. Map the principal at each hop and test whether logs connect the originating agent to the target result. Revocation needs the same path view: disabling an upstream token may stop new calls without ending an open target session or queued action. If the target can terminate those sessions, verify it; if not, keep high-impact work human-mediated or restrict the action path. That adds NOC effort, but is safer than treating a connector disable as end-to-end containment.

## Data becomes a route, not just a repository

Operators hold information whose value and sensitivity can increase when records are combined. A service map joined with alarms, customer impact, maintenance history and supplier notes can show which customers or circuits depend on a network domain, shared route or supplier. Customer records may reveal locations or operational priority. Network records can be sensitive even when they contain no personal data.

An agent can search a retrieval system, read a ticket, query service inventory and summarize results in a chat window. That can save time, but it may also send information to a supplier service or retain it in logs, prompts, traces or memory after the task ends.

The access review should establish whether the agent needs each data type, whether a source is trustworthy for the task, and whether the destination is approved. Access to every customer record is excessive if the task needs only one account. A knowledge base that mixes public guidance with internal configuration must preserve the distinction.

**Choose the processing boundary.** Keeping a workflow in an operator-managed environment may reduce one supplier data path, but it still needs updates, privileged support, logs, backups and connectivity; it also consumes engineering and compute capacity. A supplier-hosted service can avoid building that path locally, but adds dependence on provider location, support access, sub-processors, retention, availability and exit terms. Restricting fields or masking identifiers is a third route: it can reduce exposure, but may remove context needed for a service-assurance answer and increase manual cross-checks. No option is automatically safer.

For topology or customer data, prefer the smallest data set processed in a location the operator can verify. Compare supplier terms with deployed routing and the paths for logs, backups and support access. Verify the runtime destination from connector configuration and available egress or audit records; verify retention and deletion separately. A successful request proves neither deletion nor every copy of the data path. If an essential route remains unknown, keep the output advisory or restrict the feature until evidence closes the gap. Change the recommendation if a smaller data view still supports the service task, or if supplier evidence and deployed settings close the unknowns without weakening fallback.

**Multi-market processing decision.** Regional correlation raises a governance point that one deployment map can hide: each market’s data owner may control a different source, while one service owner relies on the regional result. Legal and Compliance should map applicable obligations by market and data type. Apply the processing-route, supplier-access and retention checks above per market; a regional endpoint label alone does not settle whether a transfer is permitted or controlled.

For an educational variant of the existing NOC-assistant situation, assume a multi-market service-assurance team wants a shared regional summary of alarms, topology and supplier cases. Assume data owners believe a first-pass correlation may need a market tag, service identifier, event time and alarm category, but not customer identity or full case attachments. That minimum has not been tested. The existing scenario does not establish cross-market transfer, legal approval or service impact.

The operator can send raw records to one regional service, run separate local instances, or filter records locally and share only an approved summary. Raw regional processing makes correlation simpler, but combines more sensitive data, increases the number of owners and supplier paths to govern, and creates a wider dependency if the service is unavailable. Local instances reduce routine transfer but duplicate compute, updates and support, and may fragment a regional incident view. Local filtering limits what moves, but requires field mapping and validation; if the summary removes information the NOC needs, analysts will return to manual cross-market lookups. That case-specific lookup should use the time-bounded path above, not silently widen routine retrieval.

Under the stated educational assumption, start with local processing of full records and a regional read-only summary containing only the fields proven necessary for correlation. Treat that summary as operationally sensitive until its fields and combinations are reviewed; aggregation alone does not make it safe to share. Keep customer identity and full supplier-case attachments local unless the data owner and Legal/Compliance approve a specific need. Do not allow the assistant to act across markets. If the filtered view does not support a reliable service decision, keep processing local and use an authorized, case-specific hand-off rather than expanding the standing feed.

Price the local filters, connector changes, market-by-market review, supplier work and NOC reconciliation before scaling; no cash saving or cost is established. Use Chapter 4’s evidence levels: supplier documentation describes intended handling, deployed-configuration review checks routes and permissions, a bounded test checks a synthetic marker and denial across market scopes, and an operational exercise checks whether the summary supports triage with fallback available. Confirm retention and deletion separately from request success. Expand the regional feed only when Legal/Compliance confirms the applicable route, the service owner validates that the limited summary is useful, and technical evidence covers prompts, outputs, logs, backups, telemetry and supplier access. If any material path remains unknown, keep that market’s raw data local and make a separate decision when evidence changes.

**Partial-region decision.** A market kept out of the regional feed must not appear as a quiet market. A missing or stale source can look like “no event” when it actually means “not observed.” Require the summary to show, for each market, whether its source is current, delayed, withheld or unavailable, with an owner and last-update time. The freshness limit is a service decision: a delay tolerated for retrospective trend analysis may be unacceptable during an incident. Do not let the assistant make a region-wide “clear” recommendation when required markets are absent or stale.

If one market’s route or field approval remains unresolved, keep its raw data local and show the coverage gap in the regional view. The local NOC can use its approved sources and hand off a case-specific, minimum summary only through an authorized path. This adds reconciliation work and may delay cross-market triage; the service owner must judge that delay against the exposure of widening routine transfer. Test the behavior with an approved synthetic event, then with one intentionally delayed or withheld source: the result should identify the missing market and suppress any unsupported region-wide conclusion. If the test cannot be performed safely, keep regional output advisory and require local confirmation. This test does not establish legal permission or prove every data route; no actual transfer, delay or service impact is established in the composite.

Narrowing data access reduces unnecessary exposure, but too little context can make a service-assurance answer incomplete. Decide which service or domain the task needs, then test whether the restricted view still supports a reliable answer. If it does not, request the minimum additional context through a separate, traceable path and keep the output advisory until the expanded scope is justified.

For an educational worked decision based on the NOC assistant, assume routine alarm summaries need one network domain, but incident diagnosis sometimes needs neighboring-domain alarms or case context. Also assume IAM can issue a separate time-bounded read identity and manual handling is available with temporary NOC backfill. Neither the just-in-time identity nor that capacity is an established case fact; no actual delay or service impact is claimed.

The operator has three routes. Standing cross-domain access avoids an approval delay, but every routine summary can reach more data than it needs and the shared identity weakens attribution. Manual lookup keeps the assistant inside its normal domain while an analyst uses approved tools; passing selected detail back to the assistant still requires authorization. This adds hand-offs, NOC workload and possible supplier delay. A separate time-bounded read role limits routine reach, but needs engineering, workflow and supplier support, and may still delay triage if approval is unclear. Record the IAM, supplier and NOC effort before scaling; this educational decision has no defensible cash estimate.

Under these assumptions, keep routine summaries confined to one domain. For an incident, request only the additional fields needed for the service decision and remove the privilege when its scope expires. The data owner confirms which fields are necessary; the service owner sets tolerable delay and fallback; the authorized service executive approves an exception within delegated authority. If approval cannot arrive within the service tolerance, define a narrow pre-authorized trigger and named deputy before the incident rather than granting permanent broad access.

Test the role at the target: an approved request succeeds, an out-of-scope request fails, expiry blocks new calls and ends relevant sessions, and logs identify the originating agent, approver, target and fields accessed. Exercise the manual hand-off and confirm NOC visibility remains. If the target cannot enforce or show expiry, do not count the role as time-bounded; use the manual path. If local exercise evidence shows approval delay would exceed service tolerance, consider a narrowly pre-authorized read role with an explicit scope and expiry. This is a conditional decision for the stated assumptions, not an operator result.

Persistent memory is a separate data path, not just an invisible part of the model. It can spare teams from re-entering context, but it may also carry service, customer or supplier details into later tasks. A supplier’s prompt/output retention statement does not necessarily describe every memory layer. Record what can be written and read, which identities and workflows can retrieve it, the retention and deletion behavior, and who can verify those boundaries: the data owner sets permitted content, while the platform or supplier owner provides evidence of scope and clearing. If persistent memory is not needed, keep context task-scoped; this may require more operator effort but avoids making old data available by default.

For a consequential workflow, use an approved synthetic marker in a safe environment. First confirm that it remains retrievable in the intended permitted scope as a positive control; then try to retrieve it from a separately scoped task or user, and test expiry and deletion. Keep the expected and observed results, scope, principal and log source. This checks one memory path, not all model behavior or every data source. If scope or deletion cannot be verified, keep sensitive data out of persistent memory and leave the workflow advisory.

Combining sources does not guarantee a consistent view of the network. A circuit or service can be represented differently in inventory, assurance, planning and billing. An agent may assemble a plausible summary from stale or mismatched records. For a consequential decision, the output needs enough provenance for a network or service owner to check it against the authoritative system. Otherwise, the risk is not only disclosure; it is acting on an incorrect picture of service dependencies.

A small source contract can keep an agent from turning conflicting records into a confident service-impact statement. Before a high-consequence workflow relies on joined data, the data owner and workflow owner can agree what the agent may use and how uncertainty is handled.

| Field | What the operator records | If it is unknown or cannot be verified |
|---|---|---|
| Task and minimum data | The decision the summary supports and the data fields needed for that task. | Remove fields without a clear purpose; do not grant broad context merely because it is available. |
| Source and authority | The system treated as authoritative for each field and the person or team that owns its meaning. | Keep the field marked unknown until the owner confirms the source; do not let the model choose between systems. |
| Provenance and freshness | Source, timestamp and any transformation applied before the output. Set an operator-defined freshness limit where age affects the decision. | Show the age or missing provenance and require a qualified person to verify the data before relying on it. |
| Join and destination | Permitted combinations, approved output destination, and the downstream system that receives the result. | Narrow the join or destination until the data path is understood; do not send an unapproved combined view to an external service. |
| Conflict and decision | Surface conflicts and name the resolver. Data owner confirms meaning; service owner judges whether the output is fit for its decision. | Show the conflict; block a recommendation or action until the data owner resolves it. |

This contract does not repair inconsistent inventories or assure the agent’s reasoning. It makes the data boundary and the human decision visible, so teams can test whether the output contains enough context without exposing every record. If the source or freshness cannot be verified, restrict the use to displaying attributed records rather than treating a joined summary as a reliable service view.

**Illustrative source-contract check.** For a high-consequence workflow, use synthetic or otherwise approved test records with one known-stale value and one intentional conflict. Confirm that the summary preserves each field’s source and timestamp and surfaces the conflict. It should withhold a service-impact recommendation until the data owner resolves the field conflict; the accountable service owner then decides whether the resulting output is fit for that service decision. Record the expected and observed output, reviewer and limits. This checks provenance and conflict handling for that workflow; it does not establish that source systems are correct, that the model is generally accurate or that the tool path is secure. If a safe check is not available, keep the summary advisory and require verification against authoritative records before service decisions.

CISA and its international partners’ May 2026 agentic-AI guidance identifies expanded attack surface as a risk and warns against broad access to sensitive data or critical systems. Its full report also describes indirect prompt injection through external data sources. For operators, retrieved content is information to assess, not an instruction that changes the agent’s authority.

For the NOC assistant, the choice is whether tickets and supplier cases stay outside its context, inform a read/draft recommendation, or can trigger a connector action. Excluding them removes one manipulation path but returns lookup and cross-check work to the NOC. Letting them inform a recommendation can preserve context, but the content itself must not grant permission; the connector or target must deny actions outside scope. On current facts, keep these sources read/draft and deny related actions at that boundary. In a safe, separated environment, test benign and hostile content to see whether it changes tool choice or destination; then verify target denial and logs tying source, principal and result. Include a manual path in case supplier-managed calls are not observable. Broaden use only when those checks and essential NOC visibility are verified. If not, restrict the tool or keep the workflow manual.

## Tools determine what an agent can do

An agent may have no direct access to a router CLI and still affect network operations. It can open a ticket, retrieve an account, query a cloud platform, create a change request, trigger a workflow or call an API that another system treats as authoritative.

An agent harness is the software layer that connects the model to data, tools and systems. Its configuration determines which tools and connectors are available, what each can access, and where human approval is required. Each added tool, data source, connector or memory store creates another path. Record that configuration in the inventory; the product name alone does not show what the agent can reach.

The critical check is whether “read-only” holds at the tool boundary. Can the agent write a ticket, change its priority, invoke a workflow or reach a management endpoint through a connector? Does the API token grant more than the interface suggests? These checks matter when untrusted content can influence which tools the software selects.

An agent that recommends an action creates a different risk from one that executes it. Teams can check a recommendation against telemetry and the normal change process. Execution needs explicit permission, limited parameters, an audit record and a reliable way to stop or roll back. In a carrier network, rollback may affect several services or require supplier support. Existing engineering controls should apply to AI-enabled changes too.

A sensible starting point is to let the agent read only the information its task requires, and to use a controlled broker for tools that can change a service or expose sensitive data. Low-impact ticket updates may be tested within explicit limits; actions that affect network state remain subject to the normal change process. Tool calls need an audit record and a reliable way to stop or roll back. Before expanding execution authority, the operator can verify that stop and rollback paths work with the teams and suppliers responsible for service dependencies.

A broker can centralize access rules and audit, but it becomes another dependency on the action path. If it fails, fail-open preserves the workflow but bypasses the boundary; fail-closed stops writes, but can also interrupt monitoring if read and action paths share it. For NOC use, keep alarm visibility on a separate read path where possible and fail closed on actions. The alternative is manual or degraded operation, which adds NOC workload and may delay restoration; define what service view remains and who can authorize emergency work. Test broker loss with a new request, an open session and a queued action. Verify target denial, logs, independent visibility and service fallback. If any path remains unobservable, do not count the broker as a proven boundary; keep high-impact actions human-reviewed until the test closes the gap.

Operational authority is not limited to router access. An agent that creates a change request or opens a vendor case can influence triage, escalation or the timing of restoration, even if another person or system performs the next step. That is a path into service operations, not just a write permission. Map the downstream workflow, the service it can affect, and the owner who will see or act on the handoff.

The NOC assistant described in Chapter 1 shows why the unit of review is the sequence, not each connector in isolation. Individually modest permissions can combine into an operational path. Trace what the next person or system does with the agent’s output and what source evidence travels with that hand-off. Include the downstream ticketing or supplier system in the map; stopping at the connector can hide where operator data and authority ultimately go.

| Path segment | Established facts | Required check and evidence owner |
|---|---|---|
| Agent to identity | The assistant used a broader service account. | IAM/platform confirms principal, credential owner, scope, duration and sharing; the workflow owner confirms minimum task scope. |
| Identity to data/tools | The account could read neighboring-domain data and open vendor cases. | Connector/platform traces APIs, fields, supplier roles and targets; the data owner confirms which fields the task needs. |
| Output to operations | The assistant proposed a visibility-reducing change; no completed network change is established. | NOC and change-process owners verify whether it remains a draft and where normal change authorization is enforced. |
| Containment | Potential reach is known; revocation behavior is not. | IAM/platform tests existing-session revocation and target-call denial; NOC/service assurance verify attribution and fallback. Route gaps to Chapter 5. |

This mapping separates known capability from unverified reach. A prompt instruction or product setting should not be counted as an authorization boundary unless the connector or target system enforces it. A normal change approval constrains only actions that pass through that process; it may not govern a vendor case, data retrieval or separate automation. Put enforcement where the service action occurs, then test the full path and retain a traceable identity across hops. If a supplier-managed hop cannot be observed, mark its reach unknown and limit use to the path that can be verified; Chapter 5 records any unresolved acceptance decision.

A vendor case can also be a data boundary. Its fields and attachments may include alarms, topology or service-impact details. The decision is whether the NOC assistant may prepare a draft, submit after human review, or submit automatically. Draft-only preserves a faster hand-off but keeps NOC review in the path. Automatic submission saves a step, yet may send operational details or trigger a supplier workflow before an operator sees the content. A human approval is meaningful only if the reviewer can inspect the exact fields, attachments, recipient and downstream action; a generic “approve” prompt is not enough.

Start with a human-reviewed draft until the data sent, supplier roles, retention and downstream workflow are visible. Measure NOC review effort and any service delay rather than assuming either is negligible; include the engineering and supplier effort to restrict fields or improve logging. If a safe test environment is available, use approved non-customer content to verify the exact case payload, destination, principal in the target logs, submission behavior and revocation. If that path cannot be observed or tested, omit sensitive fields or keep submission manual. Move to automatic submission only when the operator can enforce the permitted fields, verify supplier access and retention, and show that the faster hand-off is worth the remaining dependency. Network changes remain subject to the normal change process.

A December 2025 guide from CISA, the Australian Signals Directorate’s Australian Cyber Security Centre (ASD ACSC), and partner agencies addresses OT systems, not every telco network domain. It recommends integrating AI into existing security frameworks, keeping human oversight for critical OT operations, and providing fail-safe mechanisms that revert to traditional automation or manual operation. Operators should establish which of their systems fall within that scope.

## Suppliers can introduce a new path without a new project

AI may arrive through a service-desk upgrade, cloud feature, network-management platform, customer-service system or supplier portal. The product name may stay the same while its data flows, model provider or available tools change. A feature can therefore alter the operator’s exposure without triggering a new AI project or security review.

The supplier diagnostic feature described in Chapter 4 is an attack-surface question here: a routine update enabled a feature that reads topology and proposes actions. The identity reaching the data, downstream target, whether the proposal can execute and whether the feature can be disabled independently remain unknown. Do not infer from “diagnostic” that the use is read-only or that normal change control technically enforces the boundary. Chapter 4 owns the feature’s decision and assurance plan.

Supplier assurance starts with what the feature can access, where prompts and outputs are processed, which sub-processors are involved, what is logged and how changes are communicated. The operator/provider boundary needs to be explicit. ACSC recommends a shared-responsibility register that separates operator controls, provider capabilities the operator must configure, and provider outcomes it must verify. Its guidance also calls for identifying AI services, agents, connectors and unsanctioned applications, and checking prompt/output retention, customer-data training use and processing location. This is cross-sector guidance, not a telco-specific requirement.

TRAI, India’s telecom regulator, published draft guidelines on responsible AI use in telecom for consultation on 30 October 2026. The proposal calls for an inventory of active, inactive and decommissioned AI systems, including each system’s source, purpose and risk classification, plus due diligence before third-party AI is acquired or used. The draft is not binding. It is a useful prompt to establish what is in use, who supplied it, what it does and how material it is to the service.

The inventory is wider than products bought centrally: it includes supplier features, internal experiments, agent runtimes, connected tools, identities and data stores.

Testing environments add another set of paths to that inventory. The ACSC’s 12 November 2026 guidance recommends a purpose-built harness and an environment separated from production, corporate networks and management infrastructure. It also calls for limited credentials and network access, verified tool controls, real-time monitoring, logs the agent cannot change, and authorized staff who can restrict or stop the test. The guide is about testing, not production deployment. A product inventory that omits test harnesses, tools and credentials can still miss where authority enters.

## Assurance follows the action path

An inventory describes potential reach; assurance tests what happens in practice. For a consequential workflow, trace a request from the agent’s identity through each data source and tool to the system that receives its output. Confirm that task-specific permissions do not expose adjacent domains, that a tool cannot silently expand the agent’s authority, and that any output affecting service remains within the normal approval process.

Revocation can also remove visibility the NOC needs. Test revocation across connected tools and confirm that monitoring and fallback remain sufficient for the service. If a supplier-managed boundary cannot be observed, keep the path restricted until evidence is available or record the gap in Chapter 5’s decision process.

A front-end tool log may show only that a request was sent, not whether the downstream system acted. If the target result is invisible, the operator cannot claim end-to-end attribution or containment. Restrict the tool to a visible action path or add an operator-controlled gateway if feasible. If neither option preserves continuity, record the evidence gap and service consequence in Chapter 5 rather than treating general supplier assurance as proof.

## Establish visibility and ownership

A service provider does not need a perfect diagram of every AI component before acting. It does need clear answers to a smaller set of questions: which AI-enabled systems can access network operations, OSS/BSS, customer data or supplier systems? Which identities do they use? What can they retrieve, change or trigger? Who owns the use and its risk? How can access be stopped or revoked?

That is the attack surface. Chapter 3 turns to a different question: can the operator recognize a threat, decide and act quickly enough to keep service running?
